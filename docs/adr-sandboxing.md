# ADR: Sandbox contracts for ext and workload

Status: accepted on 2026-11-19 and revised on 2026-11-22. The sandbox contract
and local launch work belong to CTO. Later phases remain planned.

## Context

ext runs code it did not write: adapters, plugin packages, evaluator programs and guest
modules. Some of it comes from a third party, some is generated by a model, and some is
pulled in as a dependency. Package trust (`engine/plugin/host/adapter`, `engine/plugin/host/store`)
decides **whether** a package may run. Nothing decides **what it can do** once it runs.

The model comes from Luis Cardoso's
[field guide to sandboxes for AI](https://www.luiscardoso.dev/blog/sandboxes-for-ai). A
sandbox is three separate decisions:

- **Boundary**: where isolation is enforced, and so what has to fail for an escape.
- **Policy**: what the code can touch inside the boundary.
- **Lifecycle**: what survives between runs.

A tight policy inside a weak boundary is still a weak sandbox, and a strong boundary with
a loose policy can still leak the workspace over the network. Most failures in agent
systems are policy leaks, not kernel escapes.

### Who runs workloads

ext is not the only place that runs code:

- [`github.com/webong/workload`](https://github.com/webong/workload) is a Go library that
  uses only the standard library. It runs long-running instances locally (Linux and macOS,
  under its companion `workload-supervisor`), in Docker or on Kubernetes. It owns leases,
  readiness, restarts, taking over processes that are still running, and confirmed
  shutdown. It already returns an error for a resource limit a driver cannot enforce,
  rather than ignoring it.
- [Xallet](https://github.com/xallet/pos) plans to adopt workload through its own Package
  adapters ([xallet/pos#1](https://github.com/xallet/pos/issues/1)) and keeps grants,
  approvals, placement and its Host Broker. Xallet also has code workload does not yet
  cover: VMs (QEMU, Apple Virtualization, UTM) with snapshots, and Windows process
  handling. [webong/workload#1](https://github.com/webong/workload/issues/1) moves restart
  decisions to the host.
- ext's own plugin sessions are not long-running instances. workload is "not a queue for
  one-time jobs", so ext launches its guests itself.

If each of these invents its own words for boundary and policy, a consumer cannot state a
requirement once and have it mean the same thing on every path.

### What ext has today

| Guest runtime | Boundary | Policy today |
| --- | --- | --- |
| `process` (`engine/plugin/host/process`) and the C engine's process launch | None beyond the OS user | The environment is scrubbed to `PATH` (plus `SystemRoot` on Windows), retained stderr is capped, and canceling a call kills the child. Filesystem, network and resources are those of the user. |
| WASI (`res/web/host/engine/wasm`, `pkg/ext-go/wasm`) | Runtime | Linear memory is limited (4096 pages by default). Directories, environment and arguments are explicit grants. The guest closes when its context is done. There is no fuel: CPU is bounded only by deadlines, and a blocking host callback cannot be interrupted. |
| yaegi (`go-source`), native Go, C shared library (`cshared`) | None: the guest runs in the host's process | yaegi checks imports against an allowlist. That is a policy inside the host's own authority, not a boundary. |
| go-plugin (`pkg/ext-go/hashicorp`) | None beyond the OS user | As for `process`. |

Other relevant facts:
- CTN refuses an evaluator unless it reports `isolation: sandboxed`
  ([evaluator adapters](evaluator-adapters.md#isolation)). That value is self-reported, and
  nothing enforces it.
- `BackendProfile` says how a backend cancels and who owns the process, but nothing about
  isolation.
- `res/graph/supervisor` has no consumers. The Go `res/graph` is being replaced by
  `lib/ledger`.

## Decision

**CTO defines the sandbox contract. workload, Ext's plugin engine, and any other runner
implement it. Consumers such as ctx, ctn, Xallet and Cymonkey choose the policy.**

| Layer | Owns |
| --- | --- |
| **CTO: contract** | The boundary levels, the policy and lifecycle vocabulary, the grant and enforcement rules, capability reporting, error codes and fixtures (sections 1 to 3) |
| **CTO: local confinement** | Confining one local process on each OS and its egress proxy (section 4) |
| **Ext libraries** | Boundary reporting in the plugin engine, WebAssembly policy, and recorded evidence in `lib/ledger` (sections 5 to 7) |
| **workload** | Drivers that implement the contract for long-running instances: confined local processes, containers (including gVisor and Kata through the runtime or `RuntimeClass` setting), and VMs. Also leases, restarts, taking over running processes, snapshots and confirmed stop (section 8) |
| **Consumers** | What each package or assignment is granted, approval, placement and audit |

This keeps containers and VM monitors out of ext, as decided on 2026-11-04, while still
giving them one shared vocabulary.

### 1. Boundary levels

Every launch reports one **boundary**, whichever runner performed it:

| Boundary | Meaning | Examples |
| --- | --- | --- |
| `in-process` | Shares the host's address space and authority | yaegi, native Go, cshared, inprocess |
| `process` | A separate process with the user's full authority | ext `process`, go-plugin, workload `local` today |
| `confined` | A separate process on the host kernel, restricted by OS policy | ext `process` with a policy (section 4); workload `local` with confinement |
| `runtime` | No syscall ABI; only the imports the host supplies | WASI |
| `container` | A process in namespaces on the host kernel, managed by a container runtime | workload `docker`, `kubernetes` |
| `kernel` | Syscalls are served by a separate kernel: a userspace kernel or a guest kernel behind hardware virtualization | workload with gVisor, Kata, or a VM driver |

The boundaries are not a ranking: they move the attack surface. A consumer states the set
it accepts, for example `{runtime, confined, kernel}` for code it does not trust, or
`{kernel}` for code from unrelated tenants. A runner that cannot meet the set refuses
with `denied`.

The evaluator `isolation` value maps onto these levels:
- `sandboxed` requires `runtime` or `kernel`, or `confined` or `container` with a
  default-deny grant on every enforced class.
- `restricted` stays as defined.
- `host` is `process` or `in-process`.

CTN keeps its rule, but checks the reported boundary and the enforced grant instead of
the adapter's own claim.

### 2. Policy and lifecycle vocabulary

A **policy** is data with these classes:

- **filesystem**: paths with `read`, `write` or `execute`. Nothing else is visible beyond
  a per-platform base that a process needs to start (the dynamic linker, runtime
  libraries, temporary directories). The base is itself a fixture.
- **network**: `none`, `proxy` (the only reachable destination is an egress proxy that
  enforces a hostname allowlist), `ports` where the boundary can enforce them, or `open`
  (anything, as a plain container network or today's unconfined process gives). Hostname
  rules exist only through `proxy`. A grant with an `open` network is never `sandboxed`.
- **process**: whether children may be created. No-new-privileges is always on.
- **devices**: none unless named. GPU passthrough is a named device and is reported as such.
- **resources**: CPU time, wall time, memory, process count, open files and bytes written.
  workload's `ResourceLimits` (memory, CPU, process count) are a subset with the same meaning.
- **environment**: the scrubbed base plus granted entries. A secret is passed as a
  reference that the runner resolves at start, never as a value in the policy.

A **lifecycle** is one of:
- `fresh`: a new temporary state, deleted afterwards.
- `workspace`: a named directory or volume kept across runs.
- `snapshot`: restore from a named snapshot before the run.

The snapshot reports what it restores: `filesystem` only, or `memory` and device state
too. A volume restore is not a VM restore, and a consumer can tell which it got.

### 3. Grants, capabilities and enforcement

The contract defines the rules every runner applies, so they behave the same everywhere:

- **Request**: what a package or definition needs, from a manifest entrypoint's `requests`
  (section 5) or a workload definition. A request never grants anything.
- **Policy**: what the consumer allows.
- **Grant**: the overlap of the two. The classes that were requested but refused are
  returned before launch, so a guest does not fail confusingly partway through.
- **Capabilities**: what a runner can enforce here, per class, with a fixed reason for
  anything missing: `unsupported`, `permission` or `tool_missing`, following rule 2 of
  [the architecture ADR](adr-architecture.md).
- **Enforcement fails closed**: a grant that needs a class the runner cannot enforce fails
  with `unsupported`, and nothing runs with weaker protection. A caller may pass an
  explicit list of classes it accepts unenforced.
- **Report**: every launch returns its boundary, the grant, and the classes actually
  enforced. ext records it (section 7), and workload puts it in each `Observation`.

### Where the contract lives

The contract is a nested CTO module, **`src/cto/sandbox`** (decision 1). It contains:
- the types;
- validation;
- the grant computation;
- the enforcement check;
- the fixtures under `src/cto/sandbox/testdata/v1`;
- its error codes, starting from the shared list in `res/system/testdata/codes.json`.

It uses **only the standard library** and imports nothing else in ext. That lets
workload, which also uses only the standard library, depend on it without taking on
`golang.org/x/sys` or anything from the plugin engine. `src/ctx/internal/arch` enforces
that `src/cto/sandbox` imports nothing from ext. Other languages read the same fixtures, under
rule 1 of the architecture ADR.

### 4. Confining a local process (CTO)

Confinement is CTO's platform implementation of its sandbox contract. It lives in
`src/cto/internal/confine`, imports `src/cto/sandbox`, and is reported as `confined`:

| OS | Filesystem and process | Network | Resources |
| --- | --- | --- | --- |
| Linux | Landlock, using the highest ABI the kernel reports, plus a seccomp allowlist (`ptrace`, `mount`, `bpf`, `perf_event_open`, `kexec_load`, `userfaultfd` and other high-risk calls denied) and `no_new_privs` | Landlock TCP port rules (ABI 4 or later); otherwise a network namespace that reaches only the proxy, when user namespaces are allowed; otherwise `unsupported` | A cgroup v2 leaf when the session's cgroup is delegated, otherwise rlimits, with what rlimits cannot cover reported as missing |
| macOS | One of two drivers (below): Seatbelt or App Sandbox | Seatbelt: deny everything except the loopback proxy port. App Sandbox: no network entitlement, or the client entitlement with the proxy as the only reachable destination | rlimits, plus a wall-time kill |
| Windows | An AppContainer token with no capabilities, plus ACL grants for the package SID on exactly the granted paths, removed afterwards | No network capabilities; loopback to the proxy through an exemption for that one SID | A job object (kill on close, process count, memory, CPU rate) |

**Confinement drivers.** An OS may have more than one mechanism. Each is a driver inside
`src/cto/internal/confine` with its own capabilities, and the consumer chooses one.
The library never picks one by name, and a launch that names no driver fails with
`invalid` when more than one is available. macOS has two (decision 3):

- **`seatbelt`**: a profile generated from the grant and applied with `sandbox_init`
  before exec. It is the only macOS mechanism that confines one child differently from
  its parent and supports filesystem grants per path. The interface is unsupported for
  third parties and deprecated as a command (`sandbox-exec`). ext accepts that risk and
  tests the profiles on each macOS release in CI.
- **`app-sandbox`**: the launch step is a separate helper signed with the App Sandbox
  entitlement (below), and the guest it starts inherits that sandbox. It is Apple's supported
  mechanism. Its grant is fixed when the helper is signed: the helper's container plus the
  entitlements it carries. It therefore reports filesystem grants per path, beyond that
  container, as `unsupported`, and a grant that needs them fails closed. It suits a
  consumer that ships its own signed helper for a known set of packages.

Linux and Windows have one driver each today (`landlock` and `appcontainer`). The same
seam takes another driver later without changing the contract.

**One launch step, `ext sandbox exec`.** Go's `os/exec` cannot run code between fork and
exec, the C engine launches processes as well, and workload's supervisor launches its own.
So none of them confines a process directly. Each runs a launch step in a separate
process:
- A runner starts `ext sandbox exec` with the grant on a file descriptor or handle,
  followed by the guest's command.
- The command applies the grant to its own process and writes the report to a status pipe.
- Then it execs the guest. On Windows, where there is no exec, it creates the guest in the
  AppContainer inside the job object and waits for it.

`src/cto/internal/confine` exposes `confine.Exec` to CTO's command implementation;
it does the three steps above in the calling process.
`src/cto/internal/app` owns the command dispatch, and the installed CTO package
provides `ext cto exec|check` and its `ext sandbox` alias. Other runners call the
installed Ext command as a launch helper or implement the public CTO sandbox contract
in their own drivers.

Some classes cannot be enforced by a process that confines itself and then becomes the guest:
a wall-time bound, and a fresh, workspace or snapshot lifecycle, need something that outlives
the guest. The runner that starts the launch step enforces those and names them in the
launch (`confine.Launch.Runner`); they are reported as enforced on its word. A plain
`ext sandbox exec` from a shell has no such runner, so a person running one either accepts
`lifecycle.fresh` unenforced (`--accept`) or is refused.

A runner only needs a command line for the launch step and the report format, which is a
fixture:
- When ext hosts the engine, the installed CTO package supplies `sandbox exec`.
- Other hosts, such as the Python or Ruby hosts, configure the path to `ext`.
- workload configures it the way it configures `workload-supervisor` today: as an absolute
  path plus arguments. So workload's library keeps using only the standard library.

The `app-sandbox` driver is the exception: `ext` cannot sign itself into App Sandbox
without confining the whole `ext`. A consumer that chooses it builds a small helper that
calls `confine.Exec`, signs it with its entitlements, and configures that helper's path in
place of `ext sandbox exec`.

### 5. The plugin engine (C first, then Go)

Following [the C engine first rule](plugin-engine-parity.md), these land in `lib/plugin`
with fixtures in `lib/plugin/testdata/v1`, then reach `cgoengine`, a regenerated
`c2goengine` and the pure-Go `engine`:

- `BackendProfile` gains `boundary`. The value is fixed per backend, except that a process
  launch reports `confined` when it went through `ext sandbox exec`.
- The process launch takes an optional grant and the command line of the launch step. With
  a grant, it runs that step.
- Selection (`interop.Resolve` and its C counterpart) accepts a set of acceptable
  boundaries. A package whose runtime cannot meet it fails admission with `denied`.
- A manifest entrypoint may carry `requests`, the classes of section 2. Being part of the
  manifest, they are covered by the trust digest. This is a manifest change, so it lands
  in both engines together.

### 6. Network egress and WebAssembly

**Egress.** None of the OS mechanisms can filter by hostname, and neither can a plain
container network. ext provides one egress proxy as a mechanism, in
`src/cto/internal/confine` (decision 4). It exists only as part of a grant and is never a
general routing service:
- an HTTP CONNECT and HTTP forward proxy on loopback;
- it allows a list of hostnames, ports and schemes;
- it reports each connection, allowed or refused;
- it has bounds on connections, bytes and time.

The consumer supplies the list, and the guest gets the address as `HTTPS_PROXY` and
`HTTP_PROXY`. workload's container and VM drivers can run the same proxy on the network
they create for an instance, so `network: proxy` means the same thing everywhere.

**WebAssembly** stays wazero's runtime boundary. ext adds:
- a deadline on each host call, separate from the call's own deadline, since a blocking
  host function is the one thing a guest's context cannot interrupt;
- host imports beyond WASI declared in `requests`;
- a plain statement in the backend's limits that CPU is bounded by wall time and is not
  deterministic (decision 5);
- optionally, running the wazero runtime inside a `confined` process, which also bounds
  compilation memory.

### 7. Evidence in `lib/ledger`

The article is blunt: "sandboxes without telemetry become incident-response theater". The
`ext.system` vocabulary gains a record for each launch. It holds:
- the runner and boundary;
- the request, grant and enforced classes;
- the process tree it produced;
- egress decisions from the proxy;
- denials the OS reports (Landlock and seccomp audit records on Linux, the sandbox log on
  macOS, access-denied failures on Windows);
- how the run ended.

The vocabulary lands as fixtures under `res/graph/testdata`, and the recorder is
`lib/ledger`'s, not the Go `res/graph`, which is not being extended. workload does not
write to the ledger: it returns reports, and the consumer, or ext when it hosts workload,
records them.

### 8. What workload builds on this

This section is direction for workload, not an ext decision. Its work is tracked in that
repository.

- **Import `src/cto/sandbox`** and describe each driver by its boundary and capabilities.
- **`local`**: becomes `confined` when given a grant, by starting the worker through
  `ext sandbox exec` under `workload-supervisor`. Windows support can come from Xallet's process
  handling.
- **`docker` and `kubernetes`**: report `container`, or `kernel` when gVisor or Kata is
  selected through the runtime or `RuntimeClass`. Translate the grant into mounts, the
  network and limits, and refuse what they cannot express.
- **VM drivers**: QEMU and Apple Virtualization (the candidates from Xallet), then libkrun
  and Firecracker. They report `kernel` and declare `snapshot` with `memory` where the VM
  monitor supports it.
- **Observations** carry the report of section 3.
- **Restart decisions** stay as in webong/workload#1. They are lifecycle ownership, not
  sandbox policy.

## What ext does not do

- **Choose a policy.** Consumers decide what is granted, and the approval UI is theirs.
- **Run containers or VMs.** Those are workload drivers.
- **Supervise long-running instances.** That is workload. `res/graph/supervisor` has no
  consumers and goes with the Go `res/graph`.
- **Mint credentials.** Issuing short-lived, scoped tokens is provider-specific and
  belongs to that provider's adapter or to the consumer.
- **Claim a boundary it did not enforce.** `in-process` stays `in-process` however it is
  wrapped ([plugin interoperability](plugin-interoperability.md)).
- **Protect against kernel bugs with `confined` or `container`.** Code from unrelated
  tenants needs `kernel`.

## Decisions

Taken by the user on 2026-11-19.

1. **The contract is CTO's nested module, `src/cto/sandbox`,** using only the standard library and
   importing nothing else in ext. Workload can depend on that module without taking
   `res/system` or the plugin engine.
2. **The launch step is CTO code.** `src/cto/internal/confine`
   exports `confine.Exec` within CTO, and the installed CTO package serves `ext sandbox exec`.
   Linux and Windows need no cgo; macOS calls `sandbox_init` through purego or cgo. A
   separate `ext-confine` executable in `res/system` was rejected because `res/` holds no
   commands, and C in `lib/` because it would have had no Go reference.
3. **macOS gets both mechanisms, as drivers:** `seatbelt` and `app-sandbox`, chosen by the
   consumer (section 4). workload's Apple Virtualization or libkrun driver remains the
   `kernel` option.
4. **The egress proxy lives in `src/cto/internal/confine`.** It exists only as part of a
   grant and never as a general routing service, so `res/system/service/network` keeps
   exposing local state only.
5. **WebAssembly CPU is bounded by wall time only,** stated as non-deterministic, until a
   consumer needs deterministic limits. Instrumenting modules, or another runtime with
   fuel, can be decided then.
6. **Xallet's VM and Windows process code moves into workload drivers,** through workload's
   own issues, not into ext. The process-identity part already exists in
   `res/system/service/process` and is reused rather than moved.

## Phases

1. **Contract.**
   - `src/cto/sandbox` with its fixtures: the levels, the vocabulary, grants, capabilities and
     reports.
   - `boundary` in `BackendProfile`, in C then Go.
   - CTN checks the boundary as well as the isolation attribute.
   - No behaviour changes, but every launch becomes honest about what it is, and workload
     can start reporting in the same words.
2. **Confinement.**
   - `src/cto/internal/confine` and `ext sandbox exec` on Linux,
     macOS and Windows.
   - Filesystem, process and resources first; network as `none` only.
   - The engines' process launch takes a grant.
   - workload's `local` driver can use it from here on.
3. **Egress, requests and evidence.**
   - The proxy and `network: proxy`.
   - Manifest `requests`, in C then Go.
   - The launch record in `lib/ledger`.
4. **WebAssembly policy.** Per-host-call deadlines, declared imports, and the optional
   confined runtime.

workload's driver work runs in parallel from phase 1 on, in its own repository.

## Consequences

- One vocabulary covers ext's guests, workload's instances and Xallet's adoption of
  workload. A consumer can require a boundary and a grant without knowing the runner, the
  driver or the OS, and can show the user what was enforced.
- Package trust and confinement become separate questions: trust decides whether something
  may run, and the grant decides what it can do.
- ext stays free of container and VM code, and workload stays limited to the standard
  library.
- CTO adds its sandbox module and local confinement package; Ext owns command
  dispatch in `cmd/ext`, one field in `BackendProfile`, and one in the manifest's entrypoints. The engine and
  manifest changes land in C first, under the rule in `AGENTS.md`.
- The per-OS base policies have to keep working as runtimes change. They are treated as
  code: versioned fixtures, tested on each OS in CI.
- On macOS, the `seatbelt` driver depends on an interface Apple does not support. The
  `app-sandbox` driver is supported but cannot grant paths one at a time. A consumer
  chooses between them knowing that trade-off (decision 3).
