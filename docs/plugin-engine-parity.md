# Shared plugin engine parity

The C engine in `lib/plugin` is the main plugin engine for every language's production
host. Go's default host now reaches its described library interface through
`cengine/plugin`, including `CGO_ENABLED=0` builds. A new host feature starts in C
and its shared fixtures. The remaining pure-Go session is a differential-test
reference, not a production fallback.

## Go host bindings

`cgoengine/plugin` preserves the public Go session API. With `ext_cengine` and cgo
it uses the linked C binding; otherwise it delegates to `cengine/plugin`, which
loads the C shared library. A missing native library is an explicit error.
`cgoengine.CEngine` is true in both builds. The data model and guest SDK remain
Go code. Installed-package consumers use `cengine/plugin/host`; the old
`engine/plugin/host` root package has been removed, while its store, transport
and adapter subpackages remain.

Go transports can supply an `engine.Backend`. The described C host's event
backend calls it for I/O while C owns admission, sessions, reverse routing and
lifecycle. Call-scoped event tags preserve Go caller context for policies,
observers and transport callbacks. `TestNativeSession` compares error and
observer behavior against the reference session, and
`TestNativeSessionPreservesCallerContextAndTransportError` protects context and
transport error propagation.

The C ABI loader (`pkg/ext-go/cengine/cguest/backend` over `pkg/ext-go/cengine/cguest`, which opens a C ABI library or a Go
`-buildmode=c-shared` guest as a backend) has two builds as well: cgo
(`loader.c`) on Linux, macOS, FreeBSD and Windows, and, without cgo,
[purego](https://github.com/ebitengine/purego) on Linux, macOS and Windows for
amd64 and arm64. The ABI has no host callbacks (the guest never calls a function
pointer of the host), so purego's callback limits do not apply. Without cgo,
FreeBSD (purego needs a special `-gcflags` flag there) and 32-bit or other
architectures report `ErrUnsupported`. Both loaders keep images resident, take
absolute verified paths only and cancel the same way, and both run the cshared
conformance tests and the shared host cases (`scripts/cshared-purego.sh`, the
`go-purego` job of the Host cases workflow). On Linux, a `CGO_ENABLED=0` program
that imports `cshared` links purego's runtime shim and is dynamically linked
against libc. On darwin/amd64 both loaders refuse a Go
c-shared guest with `ErrUnsupported` (detected by its `_cgo_wait_runtime_init_done`
export, before any call): each Go runtime keeps g in the same fixed TLS slot
there, so the guest's runtime takes the host's g for its own and faults. C, Rust
and Zig guests load there as anywhere else.

### Running the comparison against an engine

The checks that compare an engine with the pure-Go engine are an importable package, `pkg/ext-go/engine/plugin/plugintest/enginetest`, and take an `enginetest.Engine`: a name,
the engine's `Call(operation, json)`, the directory of the shared fixtures and, to compare instance
managers, sessions and child processes, `NewInstances`, `Open` and `OpenProcess`. There are 28
checks:

- the pure services: descriptor, request, response, frame, manifest, schema and endpoint
  validation, descriptor matching and case folding, among them the pairwise, multi-field and
  generated-schema differentials (19, driven by `Call`);
- the instance manager's error causes and events (2, `NewInstances`);
- the session's error causes, admission failures, drains and observer events (6, `Open`);
- the events and error classes of 14 ways admitting a child process the engine starts can go
  (1, `OpenProcess`; a test binary serves as the plugin, see `MaybeServeGuest`).

Two engines run them. The cgo engine's runs are in `pkg/ext-go/cgoengine/engine_checks_test.go`,
under the names the checks have always had (`TestPairwiseMutationDifferential` and the rest). The
translated engine (`pkg/ext-go/c2goengine`: the same C, translated to Go by ccgo) runs all 28 in
`c2goengine_test.go` on darwin and linux, also under the race detector; on Windows it translates the
services only, so the checks that need `EngineCall` run there and the session, process and instance
checks are skipped. A check whose constructor an engine leaves out is skipped, and a check that passes
for an engine passes for the same reasons. The pure-Go engine also runs the instance and session
checks against itself, which shows the checks' own mechanics and timing do not flake. The checks use
the pure-Go engine as the other side of each comparison because it needs no C toolchain; a difference
they find is settled by the C engine and the fixtures, not by the side the harness happens to call
first.

The stream, capability, progress and reverse-call differentials still live in the `cgoengine`
package, because they need progress frames and reverse calls, which the harness has no interface
for yet.

## Required destination

CTX is in development. The C engine is the main engine; where it still lacks
behavior or platform coverage that the pure-Go engine has, the gap is closed in C,
and the pure-Go implementation is retired only once nothing depends on it. Parity is a requirement, not an optional follow-up. ABI and internal API
changes are acceptable during this work; every language binding must be updated
together. The plugin wire contract remains independently versioned.

The destination is one implementation of common engine behavior with idiomatic
language bindings. Runtime backends may use the runtime that owns their mechanism:
HashiCorp, native Go and Go source interpreted by yaegi (`pkg/ext-go/yaegi`) remain Go integrations. A non-Go host reaches those through
an explicit bridge or runtime module, not by silently embedding Go into the C
core. Guests may implement the public wire contract without linking any engine.

## Definition of parity

Parity means matching observable behavior and failure semantics, not merely
successfully calling a guest. A callable Go backend behind C is runtime reachability;
it does not establish portable C implementation or complete SDK parity.

The existing Go implementation and its conformance cases are the baseline. Every
row below needs shared evidence across relevant linkage modes and language
bindings before it can be marked complete. Nothing in this document declares
full parity achieved.

## Implementation order

1. Backend extension boundary and C-owned lifecycle; reuse existing Go runtimes
   through this boundary while implementing shared mechanics.
2. Complete host contract, cancellation, selection, requirements and observation.
3. Portable guest engine, typed language authoring and shared schema semantics.
4. Stream/capability, instance, package and route APIs.
5. Complete backend/platform coverage and language bindings.
6. Run differential conformance, lifecycle/race/sanitizer and representative
   performance checks. Switch public Go APIs to bindings, then delete duplicated
   mechanics once the evidence covers their replacement.

Do not remove working Go paths or claim the C engine is the default SDK before
these requirements are met. Static linkage is already the default *distribution
choice for consumers of the C engine*; it is not a completed SDK migration.

## Evidence for the current increment

The C engine verifies installed package entries through `ext_plugin_store_digest` and
persists scoped trust records through `ext_plugin_trust_state_of`, `ext_plugin_trust_record`,
and `ext_plugin_trust_revoke`. The Go binding and the pure-Go reference share the file
format. ext adapters migrate their legacy trust records once; Ext commands and
CTN inference providers use separate scopes. Install, upgrade, replace, remove and
load, whole-root list, verify and unverified listing, and layered roots now also exist in the C store (see
the Packages and trust row), and the engine-routed Go store (`cgoengine/plugin/host/store`) runs on it; the pure-Go
store stays the standard-library baseline, entrypoint resolution (`ResolveEntrypoint`, "discovery") runs in C and

the layered view and `ResolveEntrypoint`.

Install from a pinned archive is in both stores. The pure-Go store has `InstallArchive`, `ExtractArchive`,
`Download` and `Receipt`; the C store has `ext_plugin_store_install_archive` and `ext_plugin_store_receipt` (`src/archive.c`

miniz's inflate decoder vendored in `lib/plugin/vendor/miniz`; `src/store.c` checks the digest, extracts below
the root, installs or upgrades and writes the receipt, and `ext_plugin_store_remove` deletes it). Both are held to
`testdata/v1/archive-cases.json` and the archives beside it: `TestArchiveCases` in Go, `tests/store_archive.c`

## Building the C engine locally

The `ext_cengine` build tag links `pkg/ext-go` against the C engine, so those tests
need the CMake library built first. `go test -tags ext_cengine ./pkg/ext-go` fails to
link with `ld: library 'ext_plugin_host_static' not found` until you do. Note that
`go build` of a library package does not link, so it appears to succeed; the
failure surfaces when `go test` builds the test binary.

The cgo directives in `pkg/ext-go/engine.go` use a bare `-lext_plugin_host_static` with no
library search path, so point the linker at your build directory:

```bash
cmake -S lib/plugin -B /tmp/lib/plugin-build \
  -DCMAKE_BUILD_TYPE=Release -DEXT_BUILD_SHARED=ON
cmake --build /tmp/lib/plugin-build -j 4

export CGO_LDFLAGS="-L/tmp/lib/plugin-build -Wl,-rpath,/tmp/lib/plugin-build"
export EXT_CENGINE_GUEST=/tmp/go-guest
export EXT_CENGINE_FAULT_GUEST=/tmp/fault-guest

go build -tags ext_cengine -o "$EXT_CENGINE_GUEST" \
  ./tests/crosslang/testdata/go-guest
go build -tags ext_cengine -o "$EXT_CENGINE_FAULT_GUEST" \
  ./pkg/ext-go/cgoengine/plugin/testdata/faultguest

go test -tags ext_cengine -race ./pkg/ext-go/cgoengine/plugin
go test -tags ext_cengine,ext_cengine_shared -race ./pkg/ext-go/cgoengine/plugin   # shared linkage
```

The two guest binaries are required: without `EXT_CENGINE_GUEST` and
`EXT_CENGINE_FAULT_GUEST` the tagged tests fail with `EXT_CENGINE_GUEST required`.

`scripts/plugin-cengine.sh` does all of the above plus the sanitizer builds,
Rust and Zig guests, and the Node addon, then uploads benchmarks. It also
requires Zig 0.17.0, which the C-only path above does not.

These are scenario-level results, not proof of full parity. CI runs on Linux, macOS and Windows. Remaining error and observer semantics,
release packaging, and the final switch
from independent SDK implementations are still required. Keep working reference
paths until these acceptance requirements are met.
